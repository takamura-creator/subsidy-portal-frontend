### 設計根拠（リサーチ）

- 待ちの体感を伸ばすのは時間そのものではなく**不確実性**。工程を刻んで「小さな完了」を複数回与えるのが最も効く（chunking）。
- **「実処理と結び付いていない偽の進捗バー」は信頼を壊す**。→ 本台本は工程の**順序を実装と一致**させ、最終工程は**応答受信まで完了させない**、バーは**応答前に 88% を超えない**。
- 進捗の見せ方は「遅→速」より「速→遅」が離脱率が低い。→ 工程1を最短(1.25s)、工程2を中(2.60s)、工程3で保持、に設計。

## Phase 2: コンセプト（核物語 3 行）

```
[起点]   URLを入れてボタンを押した。……押せたのか？ 動いているのか？ 手元は無反応、変化は視界の外。
[転換点] 押した瞬間、手元のフォームが「診断卓」に変わる。亀が虫眼鏡を持って自分の会社を調べに走り、
         その手順が押した指のすぐ下で 1 段ずつ進んでいく。
[着地点] 待たされたのではなく「立ち会った」。出てきた結果は、自分のために動いた成果物として届く。
```

**主役**: 機器でもUIでもなく「**AIが自分の会社のために働いている実感**」。亀はその働き手の擬人化として起用する（主役化ではなく作業者としての配置）。

### 大袈裟さの三点セット（同時発火・これが台本の骨）

1. **画面上端**: フルワイド 3px 進行バー（スクロール位置を問わず「動いている」）
2. **手元＝左カラム**: フォーム直下に**解析コンソール**が開く（押した指のすぐ下＝視線が既にある場所。モバイルの「視界内保証」もこれで解決）
3. **視線の橋渡し**: ボタン → プレビューカードへ**送信ビーム**が走り、右カードが**受信パルス**＋**解析中リング脈動**で応答する（「変化が右だけ」問題を、左→右の因果として結線して解く）

## 終わり方 ②：エラー（E）— 既知チケット「解析中表示が残る」の解を兼ねる

**根本原因**: `HeroClientShell` がエラー時も `submittedUrl` を保持し、`HeroLivePreview` の `livePhase` が `url && !diagnoseResult → "analyzing"` と導出されるため、解析中のまま固まる（`HeroLivePreview.tsx` L53-56）。
**解**: 親に明示的な状態機械を置き（Phase 6 §3）、`error` / `aborted` では**必ず右カードを `idle` に落とす**。

### エラー理由行（ステータス別・一字一句確定）

| status | 理由行（13px / `--hc-text`） | 主ボタン(primary) | 副ボタン(secondary) |
|---|---|---|---|
| 422 | `ホームページの情報を読み取れませんでした。` | `手入力で診断する` → `/match` | `もう一度試す` |
| 429 | `アクセスが集中しています。1分ほどおいてから、もう一度お試しください。` | `もう一度試す` | `手入力で診断する` |
| 408 | `30秒以内に解析が終わりませんでした。` | `もう一度試す` | `手入力で診断する` |
| その他 / 0 | `通信エラーが発生しました。接続をご確認ください。` | `もう一度試す` | `手入力で診断する` |

> 422 のみ主従を入れ替える理由: HP から読み取れない以上、再試行しても同じ結果になる公算が高い。同じボタンを押させ続けるのは不誠実。

### 5.4 reduced-motion（`prefers-reduced-motion: reduce`）

**無効化**: 発火リング / 走査光 / 送信ビーム / 受信パルス / 解析中リング脈動 / 亀の待機モーション・nod・pop / スピナー回転 / コンソールの展開アニメ / スムーススクロール（`behavior:"auto"`）。

**それでも「解析中」が伝わる静的代替（必須）**:

1. コンソールは**アニメーションなしで即時表示**（0.120s に `display` 切替のみ）。
2. 工程状態は**記号＋文字**で示す（`－ 待機中` / `● 処理中` / `✓ 完了` / `！ 中断`）。色に依存しない。
3. `経過 0:03` の**数字が 1 秒ごとに更新**される（動きではなく情報更新のため許容）。
4. 上端バーは `transition` なしで **0 / 25 / 50 / 75 / 100%** の 5 段階のみ離散更新。
5. ボタン文言 `解析中…` と `aria-busy` は通常時と同じく機能する。
6. `aria-live="polite"` により工程切替を 1 段につき 1 回だけ読み上げる。

### 6.3 状態機械（既知チケットの解・実装の正）

```ts
type AnalysisState =
  | { kind: "idle" }
  | { kind: "analyzing"; url: string; startedAt: number; attempt: number }
  | { kind: "success";   url: string; result: DiagnoseResponse; attempt: number }
  | { kind: "error";     url: string; status: number; attempt: number; consecutiveFailures: number }
  | { kind: "aborted" };
```

| 現在 | イベント | 次 | 演出 |
|---|---|---|---|
| idle | submit(url) | analyzing(attempt=1) | A → B |
| analyzing | 応答 200 | success | S |
| analyzing | 応答 4xx/5xx/timeout/network | error | E |
| analyzing | 中止クリック | aborted | A' |
| success | submit / 「もう一度診断する」 | analyzing(attempt+1) | R |
| error | 「もう一度試す」/「もう一度診断する」 | analyzing(attempt+1, consecutiveFailures 継承) | R |
| error | 「手入力で診断する」 | （遷移なし） | `/match` へ router.push |
| aborted | submit | analyzing(attempt=1) | A → B |

**プレビューカードの phase 導出（修正後・これが解）**:

```
mode !== "live"            -> "idle"
state.kind === "analyzing" -> "analyzing"
state.kind === "success"   -> "done"
それ以外(error/aborted/idle) -> "idle"     // ← 解析中表示が残る不具合の閉塞点
```
